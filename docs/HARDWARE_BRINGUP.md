# Hardware bring-up & acceptance (phase 3)

Phase 3 built two SWD backends but could not be functionally verified without
hardware. Run this guide once a board and a target are available.

## Backends

- **Bitbang** (`CONFIG_PROBE_SWD_BITBANG`): upstream-proven `zephyr,swdp-gpio` driver.
  Try this **first** — the only new code is the thin adapter in `src/dap/swdp_driver.cpp`.
- **PIO** (`CONFIG_PROBE_SWD_PIO`, default): ported `probe.pio` / `sw_dp_pio.c` driver in
  `drivers/dp_pio/`. Performance parity with the original debugprobe firmware.

Both backends share the same `dap::SwdDriver` adapter; switching is purely a build-time
choice (Kconfig + devicetree `status`).

## Switching to the bitbang backend

The default build selects the PIO backend. To build with bitbang instead:

1. In `prj.conf`, change `CONFIG_PROBE_SWD_PIO=y` to `CONFIG_PROBE_SWD_BITBANG=y`.
2. In the board overlay (`boards/<board>.overlay`), flip the two `status` values:
   - `swd_bitbang`: change `status = "disabled"` to `status = "okay"`.
   - `swd_pio`: change `status = "okay"` to `status = "disabled"`.
3. Rebuild: `scripts/build_all.sh`.

Revert both changes to return to the PIO backend.

## Steps (run per backend, per board)

### 1. Build

```bash
# PIO backend (default)
bash scripts/build_all.sh

# Bitbang backend: edit prj.conf + board overlay as described above, then:
bash scripts/build_all.sh
```

### 2. Flash

Hold BOOTSEL, connect USB; the board mounts as a mass-storage device.
Copy the UF2:

```bash
cp build/<board>/zephyr/zephyr.uf2 /Volumes/RPI-RP2/
```

Replace `<board>` with `rpi_debug_probe`, `rpi_pico`, or `rpi_pico2`.

### 3. USB descriptor check

```bash
python3 tools/conformance/check_descriptors.py
```

Expected: passes (USB layer is unchanged from phase 2).

### 4. openocd functional test against a real ARM target

Connect the probe to a target board (e.g. another Pico, an STM32 Nucleo).

```bash
openocd \
  -f interface/cmsis-dap.cfg \
  -c "adapter speed 1000" \
  -f target/<chip>.cfg
```

Common target configs: `target/rp2040.cfg`, `target/stm32f4x.cfg`.

In a second terminal, connect with gdb:

```bash
arm-none-eabi-gdb
(gdb) target extended-remote :3333
(gdb) monitor reset halt
(gdb) info registers
(gdb) x/4xw 0x20000000
(gdb) load <program>.elf
(gdb) monitor reset run
(gdb) break main
(gdb) continue
```

Expected: connect, halt, memory/register read/write, flash, reset, breakpoint — all pass.

### 5. PIO backend only: timing / throughput check

Once the basic functional test passes with PIO, raise the adapter speed toward the
original debugprobe's operating clock:

```bash
openocd -f interface/cmsis-dap.cfg -c "adapter speed 24000" -f target/<chip>.cfg
```

Flash a moderately sized binary and compare elapsed time against the original
debugprobe firmware at the same clock. Target: within ~10% of the original.

### 6. Record results

Open a GitHub issue or append to this file documenting:
- Board and target chip used.
- Backend tested (bitbang / PIO).
- openocd version and adapter speed.
- Pass/fail for each step above.
- Any timing delta vs the original (PIO only).

## If PIO misbehaves

Use the bitbang backend as the fallback while investigating. PIO timing bugs most
likely live in one of three places:

| Symptom | Where to look |
|---|---|
| Wrong clock frequency | `sw_set_clock` clock-divider formula in `drivers/dp_pio/swdp_pio.c` vs `probe_set_swclk_freq` in `probe.c:61-72` |
| ACK not read / garbled data | Turnaround counts in `sw_configure` / `SWD_Transfer` in `swdp_pio.c` vs `sw_dp_pio.c:110-208` |
| Line stays driven / Hi-Z wrong | Side-set / pindir setup in `sw_port_on` vs `probe_sm_init` in `probe.c:151-180` |

The PIO program itself (`drivers/dp_pio/probe_pio.h`) is generated by pioasm from the
original `.pio` source and is never hand-edited; regenerate and diff at any time:

```bash
bash scripts/gen_pio.sh
git diff drivers/dp_pio/probe_pio.h   # should be empty
```

If the diff is not empty, the committed header has drifted from the `.pio` source —
re-run the script and commit the regenerated file.

## Per-board notes

| Board | Backend | Key difference |
|---|---|---|
| rpi_pico | Both | Shared SWDIO pin (GP3 = out + in); no separate SWDI. |
| rpi_pico2 | Both | Same pin assignments as rpi_pico; RP2350 silicon. |
| rpi_debug_probe | Both | Separate SWDI input (GP13) alongside SWDIO output (GP14). PIO uses `din-gpios`. Highest-risk PIO path — verify on hardware first. |

On all three boards the PIO driver loads **`probe.pio`** (1-bit side-set). The
`probe_oen.pio` path (2-bit side-set with output-enable) is latent — it activates only
if a board overlay includes `oen-gpios`, which none of the three shipped boards do.
