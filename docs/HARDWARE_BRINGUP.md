# Hardware bring-up & acceptance (phase 3)

Phase 3 built two SWD backends but could not be functionally verified without
hardware. Run this guide once a board and a target are available.

## Backends

- **Bitbang** (`CONFIG_PROBE_SWD_BITBANG`): upstream-proven `zephyr,swdp-gpio` driver.
  Try this **first** — the only new code is the thin adapter in `src/dap/swdp_driver.cpp`.
- **PIO** (`CONFIG_PROBE_SWD_PIO`, default): ported `probe.pio` / `sw_dp_pio.c` driver in
  `drivers/dp_pio/`. Performance parity with the original debugprobe firmware.

Both backends share the same `dap::SwdDriver` adapter; switching is purely a build-time
choice (Kconfig + devicetree `status`).

## Switching to the bitbang backend

The default build selects the PIO backend. To build with bitbang instead:

1. In `prj.conf`, change `CONFIG_PROBE_SWD_PIO=y` to `CONFIG_PROBE_SWD_BITBANG=y`.
2. In the board overlay (`boards/<board>.overlay`), flip the two `status` values:
   - `swd_bitbang`: change `status = "disabled"` to `status = "okay"`.
   - `swd_pio`: change `status = "okay"` to `status = "disabled"`.
3. Rebuild: `scripts/build_all.sh`.

Revert both changes to return to the PIO backend.

## Steps (run per backend, per board)

### 1. Build

```bash
# PIO backend (default)
bash scripts/build_all.sh

# Bitbang backend: edit prj.conf + board overlay as described above, then:
bash scripts/build_all.sh
```

### 2. Flash

Hold BOOTSEL, connect USB; the board mounts as a mass-storage device.
Copy the UF2:

```bash
cp build/<board>/zephyr/zephyr.uf2 /Volumes/RPI-RP2/
```

Replace `<board>` with `rpi_debug_probe`, `rpi_pico`, or `rpi_pico2`.

### 3. USB descriptor check

```bash
python3 tools/conformance/check_descriptors.py
```

Expected: passes (USB layer is unchanged from phase 2).

### 4. openocd functional test against a real ARM target

Connect the probe to a target board (e.g. another Pico, an STM32 Nucleo).

```bash
openocd \
  -f interface/cmsis-dap.cfg \
  -c "adapter speed 1000" \
  -f target/<chip>.cfg
```

Common target configs: `target/rp2040.cfg`, `target/stm32f4x.cfg`.

In a second terminal, connect with gdb:

```bash
arm-none-eabi-gdb
(gdb) target extended-remote :3333
(gdb) monitor reset halt
(gdb) info registers
(gdb) x/4xw 0x20000000
(gdb) load <program>.elf
(gdb) monitor reset run
(gdb) break main
(gdb) continue
```

Expected: connect, halt, memory/register read/write, flash, reset, breakpoint — all pass.

### 5. PIO backend only: timing / throughput check

Once the basic functional test passes with PIO, raise the adapter speed toward the
original debugprobe's operating clock:

```bash
openocd -f interface/cmsis-dap.cfg -c "adapter speed 24000" -f target/<chip>.cfg
```

Flash a moderately sized binary and compare elapsed time against the original
debugprobe firmware at the same clock. Target: within ~10% of the original.

### 6. Record results

Open a GitHub issue or append to this file documenting:
- Board and target chip used.
- Backend tested (bitbang / PIO).
- openocd version and adapter speed.
- Pass/fail for each step above.
- Any timing delta vs the original (PIO only).

## If PIO misbehaves

Use the bitbang backend as the fallback while investigating. PIO timing bugs most
likely live in one of three places:

| Symptom | Where to look |
|---|---|
| Wrong clock frequency | `sw_set_clock` clock-divider formula in `drivers/dp_pio/swdp_pio.c` vs `probe_set_swclk_freq` in `probe.c:61-72` |
| ACK not read / garbled data | Turnaround counts in `sw_configure` / `SWD_Transfer` in `swdp_pio.c` vs `sw_dp_pio.c:110-208` |
| Line stays driven / Hi-Z wrong | Side-set / pindir setup in `sw_port_on` vs `probe_sm_init` in `probe.c:151-180` |

The PIO program itself (`drivers/dp_pio/probe_pio.h`) is generated by pioasm from the
original `.pio` source and is never hand-edited; regenerate and diff at any time:

```bash
bash scripts/gen_pio.sh
git diff drivers/dp_pio/probe_pio.h   # should be empty
```

If the diff is not empty, the committed header has drifted from the `.pio` source —
re-run the script and commit the regenerated file.

## Per-board notes

| Board | Backend | Key difference |
|---|---|---|
| rpi_pico | Both | Shared SWDIO pin (GP3 = out + in); no separate SWDI. |
| rpi_pico2 | Both | Same pin assignments as rpi_pico; RP2350 silicon. |
| rpi_debug_probe | Both | Separate SWDI input (GP13) alongside SWDIO output (GP14). PIO uses `din-gpios`. Highest-risk PIO path — verify on hardware first. |

On all three boards the PIO driver loads **`probe.pio`** (1-bit side-set). The
`probe_oen.pio` path (2-bit side-set with output-enable) is latent — it activates only
if a board overlay includes `oen-gpios`, which none of the three shipped boards do.

## Full on-target acceptance (phase 5)

Run this acceptance suite per board × per backend and record results in
`docs/PROJECT_STATUS.md`.  All commands assume the repo root as the working
directory.

> **Target note:** a multidrop RP2040 (e.g. Pico-as-target) fails the
> `connect` + `reset halt` sequence even under the official debugprobe v2.3.1
> (A/B-proven on the same hardware).  Use a **single-drop SWD target** such as
> an STM32 Nucleo or a bare Cortex-M evaluation board.

### Boards and backends

| Board | PIO (default) | Bitbang (`CONFIG_PROBE_SWD_BITBANG`) |
|---|---|---|
| rpi_pico | build normally | edit `prj.conf` + board overlay (see [Switching to the bitbang backend](#switching-to-the-bitbang-backend)) |
| rpi_pico2 | build normally | same overlay flip |
| rpi_debug_probe | build normally | same overlay flip |

### 1. openocd acceptance flow

Connect the probe to a single-drop SWD target, then run openocd:

```bash
openocd \
  -f interface/cmsis-dap.cfg \
  -c "adapter speed 1000" \
  -f target/<chip>.cfg
```

In a second terminal, use arm-none-eabi-gdb or telnet to drive the sequence:

```
monitor reset halt
reg
mdw 0x20000000 4          # read 4 words from RAM
mww 0x20000004 0xdeadbeef # write to RAM
mdw 0x20000004            # verify written value
load <program>.elf        # flash program and verify_image implicitly
monitor reset run
break main
continue                  # run to breakpoint
step                      # single-step
```

Expected for each step: connect (openocd reports `Info : CMSIS-DAP: ...`),
`reset halt` succeeds, register dump shows PC + SP in valid range, RAM round-trip
echoes the written word, flash program + verify pass, `reset run` releases the
target, breakpoint + step work.

### 2. UART-bridge round-trip

Wire GP4 (uart1 TX) to GP5 (uart1 RX) as a loopback.  Open the CDC-ACM serial
port on the host and send data at two baud rates:

```bash
# 115 200 baud  (pyserial does NOT expand globs — resolve the port first)
python3 - <<'PY'
import serial, time, glob
port = glob.glob('/dev/tty.usbmodem*')[0]   # pick the CDC-ACM port explicitly
p = serial.Serial(port, 115200, timeout=1)
p.write(b'hello\n'); time.sleep(0.1); print(p.read(64))
PY

# repeat at a second baud, e.g. 9600
```

Expected: every byte written is echoed back (TX→RX loopback), at both baud
rates, with no framing errors.

### 3. Autobaud detection

> **Hardware required:** an external UART source connected to GP5 (uart1 RX).
> This step cannot be completed with a pure loopback.

1. Open the CDC-ACM port at the sentinel baud rate 9728 (MAGIC_BAUD) — this
   activates autobaud mode.
2. Drive uart1 RX (GP5) from a known UART source at the target baud rate.
3. The firmware measures the line rate, reconfigures uart1, and logs the detected
   baud.
4. Confirm the CDC↔uart1 bridge is alive and passes data at the newly detected
   rate.

### 4. LED checks

| Board | LED | Expected behaviour |
|---|---|---|
| rpi_debug_probe | DAP connect LED | lights when openocd connects |
| rpi_debug_probe | DAP run LED | lights when target is running (not halted) |
| rpi_debug_probe | UART TX LED | blinks on CDC→uart1 traffic |
| rpi_debug_probe | UART RX LED | blinks on uart1→CDC traffic |
| rpi_pico / rpi_pico2 | onboard LED | follows DAP connect state |

Verify by observing LEDs while running the openocd acceptance flow (step 1) and
the UART round-trip (step 2).

### Troubleshooting: RP2040 target won't connect (`Failed to connect multidrop`)

An RP2040 **target** requires multidrop SWD. If openocd reports
`Error: Failed to connect multidrop rp2040.dap0`, run `-d3` and look at the
switch sequence:

```
cmsis_dap_swd_switch_seq(): DORMANT-to-SWD
cmsis_dap_swd_read_process(): SWD ack not OK @ 0 JUNK   <-- garbage ACK, repeated
```

**Root cause (resolved 2026-06-12 on the bring-up rig): a dirty target state, NOT
the probe and NOT signal integrity.** While the target was running user code that
reconfigured its SWD pads, the dormant→SWD multidrop wake-up returned a JUNK ack
and a legacy connect read a garbage `DPIDR 0x10212927`. Speed sweeps
(100/200/500/1000 kHz) and `connect_assert_srst` did not help, and the **official**
`debugprobe_on_pico.uf2` v2.3.1 failed identically — confirming the probe firmware
is not at fault. **The fix:** put the target into a clean state. With the target
RP2040 held in **BOOTSEL** (bootrom owns the cores; nothing reconfigures the SWD
pads), the multidrop DP connects on the first try, reads the genuine
`DPIDR 0x0bc12477`, detects the Cortex-M0+, and the full acceptance (halt, step,
mem R/W, flash erase/program/verify, reset run) passes.

Remedies, in order of effectiveness:
1. **Put the target in a clean state** — power the target RP2040 with its BOOTSEL
   held (bootrom owns the cores), or wire the probe's RUN/nRESET to the target's
   RUN pin and use connect-under-reset. This resolved it here.
2. **Use a single-drop SWD target** (STM32 / nRF / bare Cortex-M) — standard SWD,
   no dormant-multidrop dance, immune to target-pad reconfiguration.
3. **If the JUNK ack persists even from a clean target**, then suspect signal
   integrity: shorten the SWCLK/SWDIO leads, add a solid common ground wire
   alongside the signals, and ensure nothing else drives GP2 (SWCLK) / GP3 (SWDIO).
